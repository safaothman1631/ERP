# Scorecard Explainer — Why these 24 metrics, how they're computed, how to triage

> Companion to [`scorecard.md`](./scorecard.md), generated by
> `scripts/world-class-scorecard.mjs`. Source of truth for thresholds:
> [`.kiro/specs/world-class-performance/validation.md`](../../.kiro/specs/world-class-performance/validation.md).

A scorecard is only useful if everyone reading it understands what each row
*measures*, why that measurement was chosen, and what to do when the row goes
red. This document is that handbook.

---

## Why 24 metrics — and only these 24

Two questions decide whether the system is world-class:

1. **Production Reality** — under real traffic on real devices, what does the
   system actually do?
2. **Long-term Maintainability** — six months from now, can the team move fast
   without breaking things?

Each question is decomposed into twelve measurable sub-questions (V-PR.1–12
and V-LM.1–12). Twelve is not a magic number — it's the count that came out
when we wrote the spec and refused to add anything we couldn't continuously
measure. Anything we could not measure with a script + cron got dropped.

The bar to add a 25th metric is high: there must be a new probe, a new
runbook, and a documented owner. The bar to remove one of the 24 is higher:
we'd be saying that aspect of the system no longer matters.

## Part 1 — Production Reality (V-PR.1–12)

These rows are filled by `scripts/production-reality-probe.mjs` (T-V.2, a
separate workstream) which writes JSON to `audit/probes/probes-<DATE>.json`.
The scorecard reads the latest file. Until the probe runs, every V-PR row is
`⚪ unknown`.

| ID | Computed by | Threshold |
| --- | --- | --- |
| V-PR.1 | OpenTelemetry → BigQuery `vitals_raw` rollup | per Requirements §5 SLO table |
| V-PR.2 | `web-vitals` lib → `/api/rum/vitals` → BQ   | LCP ≤ 2000 / INP ≤ 150 / CLS ≤ 0.05 |
| V-PR.3 | Sentry session tracking + 5xx counter        | ≥ 99.5% sessions crash-free |
| V-PR.4 | Per-device heartbeat → `/api/health/offline-sync` | ≥ 99.9% sync within 5 min |
| V-PR.5 | RUM `performance.mark('pos:print:*')`        | p95 ≤ 200 ms |
| V-PR.6 | Cloud LB + Cloud Run logs                    | ≥ 99.5% availability |
| V-PR.7 | Cloud Run cold-start metric + OTel lifespan  | p95 ≤ 2 s with min-instances=1 |
| V-PR.8 | `redis_cache_hits_total` / (hits + misses)   | ≥ 60% in steady state |
| V-PR.9 | Synthetic probe (`curl -H 'Accept-Encoding: gzip'`) | shell ≤ 350 KB gz |
| V-PR.10 | Sentry events tagged `kind=chunk-load-failure` | < 0.5% sessions |
| V-PR.11 | OTel spans on the Firestore wrapper          | p99 ≤ 400 ms |
| V-PR.12 | `backup-verify.yml` + scheduled job          | ≤ 24 h between successful backups |

### Triaging a red V-PR

1. Open the runbook linked on the row.
2. Identify the deploy/PR most likely responsible (Top regressions section).
3. If the metric is over budget for > 14 days, file a follow-on spec — the
   apparatus has revealed a structural problem, not a transient one.

## Part 2 — Long-term Maintainability (V-LM.1–12)

These rows are filled directly by the scripts in this repo. Each row links to
both the script (so you can run it locally) and the validation spec section
(so you can read the threshold history).

### V-LM.1 — File Size Budget

- **Source:** `scripts/audit-loc.mjs` → `docs/audit/monolith-watchlist.json`
- **Threshold:** ≤ 400 LOC advisory, ≤ 600 LOC hard limit (with
  `// monolith-budget-exempt: <ADR>` escape hatch).
- **Why:** A file you can't fit on one screen is a file you can't review.
  Beyond ~600 LOC, refactors stop happening because the file is "too scary."
- **Triage red:** Top of `monolith-watchlist.json` is the worst offender.
  Decompose into modules with clear boundaries; do not merely shuffle code.

### V-LM.2 — Cyclomatic Complexity Cap

- **Source:** ESLint built-in `complexity` rule (FE), `radon cc` (BE).
- **Wrapper:** `tools/eslint-rules/complexity-cap.js` centralises the
  threshold; `scripts/complexity-radon.sh` writes the Python report.
- **Threshold:** ≤ 15 per function (Sonar's recommended).
- **Why:** Above 15, branch coverage in tests becomes practically impossible
  and humans start missing edge cases on review.
- **Triage red:** Extract the inner branches; introduce a strategy object or
  early returns. Don't just suppress the rule.

### V-LM.3 — Cognitive Complexity Cap

- **Source:** `eslint-plugin-sonarjs` rule `cognitive-complexity` (not yet
  wired — currently `unknown`).
- **Why:** Cyclomatic complexity counts branches; cognitive complexity counts
  how hard a *human* finds it. Nested ternaries and shadowed names hurt
  cognition without hurting cyclomatic count.
- **Follow-up:** Install the plugin and turn the rule on at 15. Add to the
  scorecard once present.

### V-LM.4 — Dead Code Rate

- **Source:** `scripts/dead-code-report.mjs` (calls `ts-prune` + `vulture`).
- **Threshold:** < 0.5% of exports are dead.
- **Why:** Dead code looks alive to grep. New contributors waste hours on
  exports nobody uses.
- **Triage red:** Delete unused exports. If a symbol is "used in tests only,"
  add a `@public-for-tests` JSDoc tag and an ignore comment.

### V-LM.5 — Dependency Freshness

- **Source:** `scripts/dependency-age-audit.mjs` (npm view + PyPI JSON API).
- **Threshold:** No dep > 12 months behind latest stable on a non-major; no
  unpatched CVE > 7 days.
- **Why:** Stale deps accumulate breaking changes that all hit at once during
  the eventual upgrade, and unpatched CVEs are an audit failure.
- **Triage red:** Bump one dep at a time. Use Dependabot for CVEs.

### V-LM.6 — Test Coverage

- **Source:** Vitest c8 → `coverage/coverage-summary.json`,
  pytest-cov → `backend/coverage.xml`.
- **Threshold:** ≥ 70% FE, ≥ 80% BE (Requirements R13.1).
- **Why:** Below 70% FE / 80% BE, refactors break things silently.
- **Triage red:** Identify the worst-covered files in
  `coverage/lcov-report/index.html`; write tests for the highest-risk first
  (handlers, state machines, money math).

### V-LM.7 — Flaky Test Rate

- **Source:** `scripts/flaky-test-tracker.mjs` (GitHub Actions runs API).
- **Threshold:** < 1% of tests are flaky; no test fails > 5% of the time.
- **Why:** Flaky tests train the team to ignore failures, which then masks
  real failures. The unit cost of a flake is ~10 minutes of attention.
- **Triage red:** Quarantine the flaky test (`.skip` with a TODO), file a
  ticket, fix within one sprint.

### V-LM.8 — Bundle Size Delta per PR

- **Source:** `.github/workflows/bundle-diff.yml` (existing workflow).
- **Threshold:** +10 KB gz per chunk = advisory; +20 KB = block without
  `[allow-bundle-growth]` in the commit message.
- **Why:** Bundle size only grows monotonically unless someone is watching;
  CI's the only watcher with eternal attention.
- **Triage red:** Use `npx vite-bundle-visualizer` to find the culprit;
  lazy-load or replace.

### V-LM.9 — Onboarding Time

- **Source:** Quarterly real-onboarding exercise (manual).
- **Threshold:** ≤ 1 working day from clone to merged PR.
- **Why:** If a new contributor takes a week to get oriented, the team is
  burning a person-week every hire.
- **Triage red:** Update `docs/onboarding/` based on the friction points the
  new hire surfaced; ban "tribal knowledge" answers.

### V-LM.10 — Feature Velocity

- **Source:** `scripts/velocity-report.mjs` (GitHub Search API).
- **Threshold:** Velocity not declining > 20% QoQ; TTM p95 < 5 working days.
- **Why:** A slowing team is a leading indicator of accruing tech debt. If
  the trend is down, find the bottleneck (review queue? CI flakes? toil?).
- **Triage red:** Compare 30d window vs 90d window in the report. If reviews
  are slow → fix reviewer load. If CI is slow → fix CI.

### V-LM.11 — Documentation Freshness

- **Source:** `scripts/doc-freshness.mjs` (git log per `.md`).
- **Threshold:** < 20% of docs > 90 days stale.
- **Why:** Old docs lie. Lies cost time. Old docs are worse than no docs.
- **Triage red:** Touch the oldest 10 docs from the report. Either update,
  archive (`docs/archive/`), or delete.

### V-LM.12 — ADR Compliance

- **Source:** `scripts/adr-compliance.mjs` (GitHub PR API).
- **Threshold:** ≥ 90% of "significant" PRs (> 20 files OR > 1000 LOC) include
  an ADR in `docs/adr/`.
- **Why:** Big PRs that don't write down *why* the change was made are landmines
  for future maintainers. ADRs are how we keep institutional memory.
- **Triage red:** Open each flagged PR; ask the author to file a retrospective
  ADR (template: `docs/adr/0000-template.md`).

## How "world-class" is decided

```
WORLD-CLASS := (greens_count ≥ 22)
               AND (no row has been red for > 14 consecutive days)
```

The 14-day grace exists because some metrics legitimately go red during
deploys or incidents and recover. The grace prevents short blips from
counting against the verdict, but a structural problem (e.g., bundle creep
that nobody fixes) will eventually exceed it.

### When to file a follow-on spec

- A row has been red for > 30 consecutive days → spec.
- Three rows are simultaneously red → spec (it's a structural issue).
- The same row goes red → recovers → goes red again ≥ 3 times within a
  quarter → spec (the underlying cause is uncontrolled).

Specs live in `.kiro/specs/<slug>/` with their own `requirements.md`,
`design.md`, `tasks.md`, and (eventually) `validation.md`.

## Determinism and trust

Two scorecard runs with identical inputs MUST produce identical output
(modulo the `generated` timestamp). If you see drift, something non-
deterministic has leaked into a sub-script — file an issue with the diff.

The trend column (⬆/⬇/➡) is computed by comparing the new row's `current_value`
against the same row in `audit/scorecards/scorecard-PREV.json`. The PREV file
is overwritten at the end of each run. The dated history files
(`scorecard-YYYY-MM-DD.json`) are never overwritten — they are the
audit trail.

## Operating the scorecard

- **Weekly:** the `.github/workflows/weekly-health-check.yml` workflow runs
  every Monday 06:00 UTC and updates the sticky GitHub issue named
  "World-Class Scorecard".
- **On-demand:** `node scripts/world-class-scorecard.mjs` from the repo root.
  Pass `--dry-run` to avoid writing files.
- **Monday review:** the team spends 15 minutes reading the scorecard. Anything
  that turned red since last week → owner names a fix or files a follow-up.
