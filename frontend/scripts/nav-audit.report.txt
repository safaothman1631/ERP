### Invariant relaxation rationale (user-approved)

The original Task 4 checklist phrased invariant 21 as "no duplicate
(surface, path) pairs". On the live registry that phrasing flagged exactly
two intentional multi-control coverages:

  - quick_create_item::/contacts
      QuickCreateMenu.customer    -> /contacts
      QuickCreateMenu.vendor      -> /contacts
  - top_bar_menu_item::/settings
      TopBar.userMenu.settings    -> /settings
      OrgSwitcher.manage          -> /settings

Both groups represent legitimately distinct UI controls that happen to
share a destination URL — the contacts list serves as the landing page for
both customer- and vendor-creation flows, and both the user-menu Settings
item and the OrgSwitcher's "Manage" link land on /settings by design. The
canonical disambiguator is the `source` field, not the surface. The user
chose to keep these multi-control coverages and to relax the invariant to
`no duplicate (source, path) pairs`, which is the meaningful "no two
registry entries describe the same control" property.

`navDestinations.ts` was NOT modified — the registry stays as-is.

Verification (frontend/scripts/nav-uniqueness-check.mjs):

  legacy   (surface, path) duplicate groups:    2  (the two intentional cases above)
  relaxed  (source,  path) duplicate groups:    0  ← gate
  Exit code:                                    0

This matches the previous checkpoint subagent's finding of
`sourcePathDuplicates=[]` and confirms the relaxed invariant holds.
